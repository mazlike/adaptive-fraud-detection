# Этап 0 — Обзор методов, выбор метрик, структура репозитория

## 1. Гипотезы (краткая выгрузка)

| Гипотеза | Утверждение |
|---|---|
| H1 | Без адаптации PR-AUC заметно падает после дрейфа; резкий дрейф hurts больше, чем постепенный. |
| H2 | Дрейф-триггерное переобучение + активное обучение восстанавливает качество быстрее и с меньшим числом меток, чем базлайн без адаптации. |
| H3 | При равном бюджете uncertainty sampling лучше случайного выбора, но прирост ограничен при сильном дисбалансе (много неоднозначных легитимных транзакций, мало мошеннических). |
| H4 | Rare-class-aware стратегия превосходит чистый uncertainty sampling по recall и PR-AUC, особенно при малом бюджете. |
| H5 | Преимущество AL над случайным выбором сжимается по мере роста бюджета. |

## 2. Семейства методов (литературный обзор)

### 2.1 Детекторы дрейфа概念 (concept drift detection)

- **ADWIN (Adaptive Windowing)** — Bifet & Gavalda (2007). Скользящее окно с автоматическим расщеплением: статистический тест (границы Хоффding-а) определяет, изменилось ли среднее значение сигнала (ошибка или скоринг модели) между двумя частями окна. При тревоге окно обрезается. Широко используется в потоковом ML (пакет `river` реализует `river.drift.ADWIN`).
- **DDM (Drift Detection Method)** — Gama et al. (2004). Контрольная карта на доле ошибок с двумя порогами: предупреждение и тревога (подобно Shewhart-чарту).
- **EDDM (Early Drift Detection Method)** — Baena-García et al. (2006). Использует расстояние (количество примеров) между последовательными ошибками; 주장о преимущество при постепенном дрейфе. **[Флаг]** Точная библиография и год издания требуют верификации — не цитирую без проверки.
- **Page-Hinkley** — Page (1954). Накопленное суммарное отклонение от среднего (CUSUM-подобный подход) на сигнале ошибок.

### 2.2 Стратегии активного обучения (active learning)

- **Uncertainty sampling** — least confidence, margin sampling (максимальная неопределённость около p = 0.5), энтропия предсказания. Классическая работа: Lewis & Gale (1994) **[Флаг]** точная формулировка/год требуют верификации.
- **Query-by-committee** — Seung et al. (1992) **[Флаг]** требует верификации. disagrement между ансамблем моделей определяет информативность образца.
- **Diversity-based** — core-set, кластеризация в пространстве признаков/эмбендингов, чтобы выбранные метки покрывали różne области пространства.
- **Imbalance-aware AL** — комбинация неопределённости и вероятности положительного класса, резервная доля бюджеса на топ по p(fraud) плюс доля на exploration (предложенное в этом проекте решение; прямых аналогий в литературе не цитирую без верификации).

### 2.3 Дисимбаланс классов (imbalanced learning)

- **Class weights / scale_pos_weight (LightGBM)** и **sample weights по стоимости ошибки** (cost-sensitive learning) — обучение с весами, пропорциональными стоимости ошибок (FP/FN). Подход стоимостно-чувствительного обучения: Zadrozny & Elkan (2001) **[Флаг]** точная цитата требует верификации.
- **SMOTE** — Chawla et al. (2002): генерация синтетических объектов меньшинства между ближайшими соседями. **[Флаг]** В потоковом режиме базовый SMOTE напрямую неприменим (требует доступности всей выборки / создаёт риск утечки будущей информации в преквенциальной схеме). Stream-варианты существуют, но не внедряются в прототип.

### 2.4 Почему ROC-AUC / accuracy не являются первичными метриками

- **Accuracy.** Доля мошенничества 0.1–2%. Модель, предсказывающая «все легитимно», имеет accuracy 98–99.9% при recall по фроду = 0. Метрика неинформативна для задачи.
- **ROC-AUC.** Интегрирует TPR/FPR по всем порогам. При сильном дисбалансе очень grandes абсолютные значения специфичности (низкий FPR на огромном большинстве легитимных транзакций) завышают ROC-AUC, тогда как на практике ограничен бюджет разметки и важна precision при малом числе выданных меток. ROC-AUC слишком оптимистичен и не отражает выгоду от выбора «правильных» объектов для разметки.
- **PR-AUC (Precision-Recall AUC).** Фокусируется на положительном (мошенническом) классе, чувствителен к precision и recall одновременно, а также к доле положительного класса. Является первичной метрикой: считается в целом по потоку и в скользящем окне (rolling-window) для отслеживания падения и восстановления после дрейфа.

Дополнительные метрики: F1 при фиксированном пороге (0.5 или подобранном на прошедших данных), recall при фиксированном бюджета разметки, число затраченных меток, время восстановления (батчей до возврата PR-AUC к X% от уровня до дрейфа), задержка обнаружения ADWIN и число ложных тревог.

## 3. Экспериментальный дизайн

2 типа дрейфа (sudden, gradual) × 3 бюджета (1%, 5%, 10%) × 3 strategiи AL (random, uncertainty, rare-aware) × 3 конфигурации (baseline, +ADWIN retraining, +ADWIN+AL) × 3 сида.
Отчёт: mean ± std по сидам; попарная проверка意义 (Wilcoxon) там, где целесообразно. Каждый результат отображается на H1–H5: confirmed / partially confirmed / rejected с доказательствами. Числа не выдумываются — если эксперимент не запущен, гипотеза не считается подтверждённой.

## 4. Допущения (assumptions), принятые на этапе 0

1. Python 3.11+ (в окружении 3.13; код пишется совместимым с 3.11 через `from __future__ import annotations`).
2. Модель по умолчанию: LightGBM (GBDT); альтернатива — логистическая регрессия.
3. ADWIN из `river` кормит за поток ошибок модели или её скоринг-сигнал.
4. Бюджет разметки задаётся долей семплов в мини-батче (`budget_fraction`) и/или жёстким общим лимитом (`total_budget`).
5. Преprocessing обучается только на прошедших данных (нет утечки будущего); пороги и гиперпараметры подбираются только на истории.
6. Реальные датасеты: IEEE-CIS (TransactionDT) или Credit Card Fraud (Time); хронологический порядок без перемешивания.
7. Synthetic generator: доля фрода 0.1–2%, sudden drift (резкая смена классико-условного распределения/границы решения в момент t0) и gradual drift (линейная или симоидная интерполяция между двумя концептами за окно width). Истинные точки дрейфа сохраняются для оценки детектора.

## 6. Риски и открытые вопросы (этап 0)

- Нет доступа к реальным файлам IEEE-CIS / Credit Card в репозитории — путь к данным задаётся в конфиге; генератор синтетического потока используется как основной источник для этапов 1–6.
- LightGBM на Python 3.13: необходимо проверить наличие бинарных колёс при установке (альтернатива — XGBoost или LogisticRegression).
- Порог F1 и уровень восстановления (recovery_level) настраиваются в конфиге; эталонный уровень PR-AUC «до дрейфа» вычисляется из пре-дрейфовой части потока.
- Метод Френк/Штакет для поправки множественных сравнений (при нескольких гипотезах) —考虑 на этапе 6.
